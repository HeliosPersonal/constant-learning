# Test plan — personal-trainer-mvp

Персональний тренер польських слів у Telegram Mini App: онбординг, щоденні session з адаптивними повтореннями, пошук у версійованому словнику, content reports з автоматичною звіркою, черга й відкат для content editor, нагадування й підсумки. План прив'язує кожен AC з [PRD.md §5](./PRD.md#5-acceptance-criteria) до тестів; колонка «Task» вказує задачу з [tasks/tasks.json](./tasks/tasks.json), у якій `implement-tasks` пише червоний тест.

## Levels

`target_surfaces: [backend-service, web-frontend]` ([sad.md](./sad.md)) — тому, крім серверних рівнів, є рівні Mini App.

| Level | Scope | Strategy (generic — no tool names) |
|---|---|---|
| Unit | Чисті доменні правила: доба learner, нормалізація й оцінка відповіді, межі інтервалу, склад session, ключ дедуплікації. | У пам'яті, фіксований годинник, без БД і мережі. |
| Integration | Модуль проти справжнього PostgreSQL: транзакції відповіді, унікальні обмеження, захоплення рядків черги з пропуском заблокованих, межа доби. | Ефемерний PostgreSQL 16 у контейнері на набір тестів; фіксований годинник; підписані тестові `initData`. |
| Contract | Межа Mini App ↔ бекенд і модулі ↔ таблиці-черги. | Кожна відповідь API валідується проти [openapi.yaml](./contracts/openapi.yaml); рядки `verification_jobs` і `notification_dispatches` — проти [events.md](./contracts/events.md); TS-типи клієнта генеруються з того самого контракту. |
| E2E-through-UI | Критичний потік, проведений через справжній інтерфейс Mini App проти справжнього бекенду. | Імітоване середовище Telegram з підписаними `initData`, бекенд на ефемерному PostgreSQL. |
| Component | Екран чи компонент Mini App ізольовано: стан → відмальований результат і взаємодії. | Рендер у тестовому harness з підміною API-клієнта на згенеровані з контракту відповіді. |
| Visual-regression | Ключові екрани у світлій і темній темі Telegram. | Знімок рендера проти затвердженого еталона; еталон оновлюється лише свідомо. |
| Load | NFR латентності й обсягу пілоту з PRD §6. | Інструмент навантаження, який уже є в репозиторії, або відповідний для стеку. |
| E2E (API) | <!-- N/A: критичні потоки покриті E2E-through-UI, а серверні гілки — integration; окремий API-рівень дублював би їх. --> | — |

**Контракт усіх операцій.** Механізм перевірки будує T02. Одна contract-сюїта проганяє кожну з 19 операцій [openapi.yaml](./contracts/openapi.yaml) і перевіряє, що успішні й помилкові відповіді збігаються зі схемами й конвертом помилки. Сюїта росте разом із задачами шару `ports` і `app`; клієнт Mini App компілюється з типами, згенерованими з того самого файлу (T34).

**Visual-regression.** Механізм еталонів будує T34. Еталони у світлій і темній темі для екранів «Сьогодні», картки нового слова, результату відповіді з diff і черги редактора (T36, T37, T38, T42).

## Edge cases / error paths

Кожен error- і authorization-AC має власний рядок вище: AC-02, AC-13, AC-27, AC-29, AC-31, AC-39, AC-41, AC-45, AC-46, AC-49, AC-50, AC-52, AC-57. Додаткові випадки, які випливають з PRD, SAD і контракту:

- Підроблені чи старші за 24 год `initData` → доступ заборонено, дані не читаються (T12, integration).
- Запит без онбордингу до «Сьогодні» чи session → learner просять спершу налаштувати тренер (T13, integration).
- Та сама відповідь двічі, зокрема паралельно з двох пристроїв → одна подія відповіді, той самий результат (T17, integration; QG-1).
- Інша відповідь на вже оцінену картку → відмова без зміни результату (T17, integration).
- Паралельний старт двох session → одна активна session (T15, integration).
- Перехід на літній і зимовий час у день нагадування → одне нагадування в правильний місцевий час (T08, T30, unit + integration).
- Два паралельні тики dispatcher → жоден рядок не надсилається двічі (T29, integration).
- Простій понад 60 хв → прострочене відправлення позначено як пропущене й не надсилається (T29, integration).
- Telegram повертає «бот заблоковано» → нагадування learner вимикаються (T29, T32, integration).
- Збій парсера довідкового джерела → report іде в ручну чергу, а не падає звірка (T25, unit).
- Повторне рішення редактора щодо закритого report → відмова, стан без змін (T27, integration).
- Конкурентний відкат і нова публікація того самого запису → один з них відхилено, вказівник узгоджений (T28, integration).
- Застарілий пошуковий запит при швидкому введенні → результат попереднього запиту не перезаписує новий (T39, component).
- Коментар content report з HTML чи скриптом → редактор бачить звичайний текст (T42, component).
- Webhook без правильного секрету → оновлення відхилено (T32, integration).
- Чужі session чи картка в відповіді, «Далі» чи «Вже знаю» → «не знайдено», нічого не змінено (T17, T18, integration).
- Оскарження чужої відповіді → «не знайдено», нічого не змінено (T24, integration).
- Черга редактора показує лише псевдонімну мітку автора, без імені й Telegram id (T27, integration + contract).
- `initData` і заголовок авторизації не потрапляють у логи ні на успішному, ні на відхиленому запиті (T12, integration).
- Повторний імпорт CSV без змін → нових версій немає (T20, integration).

## NFR validation (load)

Інструмент — той, що вже є в репозиторії, або відповідний для стеку (T49). Профіль: один екземпляр, словник на 2 000 записів, 100 learner по 1 000 слів.

- **Обсяг пілоту ≥ 100 одночасних learner** → 100 віртуальних learner 15 хв: відкриття «Сьогодні», session із 20 відповідей, 10 пошуків; помилок немає, а всі пороги нижче виконуються.
- **Latency p95 оцінки відповіді ≤ 500 ms** → у тому самому прогоні серверна метрика оцінки p95 ≤ 500 ms.
- **Latency p95 пошуку ≤ 300 ms** → запит на кожен символ з 1–5 символів, серверна метрика пошуку p95 ≤ 300 ms.
- **Latency p95 «Сьогодні» ≤ 1 500 ms** → під тим самим навантаженням клієнт у браузері відкриває trainer 50 разів; p95 телеметрії `today_ready_ms` ≤ 1 500 ms.
- **Точність нагадувань ≥ 99% у межах 2 хв** → 1 000 нагадувань, запланованих на одну хвилину, з реальним годинником і заглушкою Telegram: ≥ 99% надіслано протягом 2 хв від запланованого часу. Тижневе вікно з PRD §6 далі вимірює журнал доставки в пілоті.
- **0 втрачених відповідей** → integration-тест подвійного й паралельного надсилання (T17) плюс звірка після load-прогону: кількість подій відповіді дорівнює кількості оцінених карток (T49).
