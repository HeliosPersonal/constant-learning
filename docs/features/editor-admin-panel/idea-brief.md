# Idea Brief — Editor & Admin Panel (back-office dashboard)

## 1. Raw idea
«Тут треба подумати, хотілося б мати повний контроль до всіх сутностей, як то слова, юзери ітд.» Потрібна адмінка для людей з роллю редактора (і окремо — адміністратора), щоб керувати контентом і користувачами з одного місця, а не руками в базі.

## 2. Problem
Сьогодні весь back-office робиться вручну — правки слів, розгляд скарг, керування учнями виконуються прямою зміною даних у сховищі. Це повільно, вимагає технічної людини для кожної дрібниці й не лишає сліду, хто що змінив. Біль накопичується в міру зростання словника та кількості учнів.

## 3. Users
- **Content editor** (1-2 людини зараз) — щодня/щотижня правлять слова, леми, приймають або відхиляють скарги на контент, збирають списки слів і CEFR-набори.
- **Admin** (1 людина) — керує обліковими записами учнів (пошук, перегляд, базові дії).
- **Learner** — не користувач панелі, але непрямо зачеплений: контент, який правлять редактори, — це те, на чому його оцінюють.

## 4. Why now
Тригера-дедлайну немає. Причина — накопичення болю: ручна робота в базі стає вузьким місцем у міру зростання словника й переходу продукту до моделі «персонального тренера», де контенту та учнів більшає.

## 5. Out of scope
- Самореєстрація нових редакторів/адмінів і повноцінне керування ролями через UI (ролі призначаються поза панеллю на старті).
- Аналітика/дашборди метрик навчання.
- Масове імпорт/експорт контенту та bulk-операції.
- Керування біллінгом, підписками, сповіщеннями учням.
- Версіонування та відкат контенту (свідомо не входить у v1 — див. §10, §13).

## 7. Strategic approaches

### Approach A — One-Page Content Fix Console
- **Thesis**: один простий екран-консоль, де редактор знаходить слово/скаргу/учня і править на місці — найкоротший шлях прибрати ручну роботу в базі.
- **For whom**: Content editor (§3) — головний бенефіціар; admin отримує базовий перегляд учнів.
- **Outcome metric**: час на одну правку контенту: з «знайти технічну людину + ручний запит у базу» (години/дні) → до «хвилини самостійно».
- **Key trade-off**: мінімум запобіжників — правка застосовується миттєво, без історії та відкату.
- **Effort signal**: S
- **Recommended?** ●

### Approach B — Closed-Loop Content Trust
- **Thesis**: повний робочий цикл довіри до контенту — кожна скарга веде до правки, кожна правка логується, зміни правильних відповідей можна відкотити.
- **For whom**: Content editor + непрямо Learner (захищений від тихих поломок оцінювання).
- **Outcome metric**: частка правок зі слідом «хто/коли/що» та можливістю відкату: 0% → 100%.
- **Key trade-off**: найвища довіра й безпека, але помітно більший обсяг і складність; надмірно для стадії без PMF.
- **Effort signal**: M
- **Recommended?** ◯

### Approach C — Role-Separated Content Control Room
- **Thesis**: повноцінна панель з чітким розділенням прав editor vs admin, окремими розділами під кожну сутність і рольовим меню.
- **For whom**: обидві ролі рівноцінно, із прицілом на зростання команди.
- **Outcome metric**: частка back-office-дій, доступних у панелі без доступу до бази: → 100% для обох ролей.
- **Key trade-off**: найкраще масштабується на команду, але передчасне інвестування у рольову інфраструктуру при 1-2 користувачах.
- **Effort signal**: M
- **Recommended?** ◯

## 8. Multi-perspective feedback

### Engineer
- A має найменшу поверхню інтеграції, але без аудиту/відкату правка контенту незворотна.
- Відкладена частина admin (керування учнями) лишає ручне звіряння в базі — технічний борг переходить, а не зникає.
- Спільний вхід для двох ролей спрощує старт, але ускладнить пізніше розведення прав.
- Миттєве застосування правок до даних, на яких оцінюють учнів, — найтонше місце за складністю наслідків.

### Executive
- A зараз: найдешевше зняти біль; C — коли пілот доведе обсяг скарг/учнів; B — після PMF.
- Немає дедлайну й немає доведеного PMF → не золотити, брати найдешевший варіант.
- Вартість згаяної можливості низька: інструмент внутрішній, не впливає на дохід напряму.
- Ризик репутації низький на пілоті, але зростає з кількістю учнів, якщо оцінювання тихо ламається.

### UX-researcher
- A — найнижча крива навчання: один екран, мінімум понять для редактора-непрограміста.
- Відсутність undo породжує «боязке» редагування — редактор вагається правити, боячись щось зламати.
- Аудит-слід (сильна сторона B) — головний UX-актив довіри, але не блокер для першого релізу.
- Розділення ролей (C) корисне, коли людей більше однієї на роль; зараз додає зайвих екранів.

### Synthesis matrix
|         | Engineer | Executive | UX |
|---------|:--------:|:---------:|:--:|
| App. A  | +        | +         | 0  |
| App. B  | -        | +         | -  |
| App. C  | 0        | 0         | +  |

- A·Eng `+`: мала поверхня, швидко будується.
- A·Exec `+`: найдешевше зняти поточний біль.
- A·UX `0`: просто, але лякає без undo.
- B·Eng `-`: великий обсяг для стадії.
- B·Exec `+`: захищає довіру до оцінювання.
- B·UX `-`: багато кроків до першої правки.
- C·Eng `0`: рольова інфраструктура передчасна.
- C·Exec `0`: інвестиція без доведеного обсягу.
- C·UX `+`: чисте розділення під кожну роль.

## 9. Trade-offs and edge cases

### Trade-offs per approach
| Approach | Pros | Cons |
|---|---|---|
| A | Найдешевше, найшвидше, найпростіше для редактора | Без історії/відкату; відкладений admin лишає ручну роботу |
| B | Захищає оцінювання, повний слід змін | Дорого й складно для стадії без PMF |
| C | Масштабується на команду, чисті ролі | Передчасна рольова інфраструктура при 1-2 людях |

### Edge cases
- Редактор править слово, на якому учнів уже оцінювали — минулі відповіді стають неузгодженими з новим «правильним» варіантом.
- Два редактори правлять те саме слово майже одночасно — чия версія перемагає.
- Скарга стосується слова, яке вже видалене/змінене іншим редактором.
- Учень зникає/деактивований, поки admin відкрив його картку.
- Слово входить одразу у кілька списків/CEFR-наборів — правка зачіпає всі.
- Порожній чи неоднозначний контент (слово без правильної відповіді) потрапляє у панель.
- Вхід у панель із недостатньою роллю (editor намагається дію admin і навпаки).
- Втрата сесії/подвійне застосування тієї самої правки.

## 10. Risks
- **Топ-ризик (адвокат диявола): тиха деградація оцінювання (silent answer-key drift).** Редактор правит «правильну відповідь», і прогрес учнів тихо стає невідповідним — без версіонування та відкату це не видно, поки не прийде скарга. **Свідомо прийнятий trade-off v1**: користувач обрав чистий Approach A без запобіжників; спосіб пом'якшення винесено в §15 як відкрите питання, а не вбудовано в реліз.
- Відкладена частина admin (керування учнями) лишає ручну роботу в базі — ризик, що «повного контролю» з §1 так і не досягнуто на v1.
- Спільний вхід для двох ролей без чіткого розведення прав — ризик випадкових дій поза роллю.
- Конкурентні правки двох редакторів без блокувань — ризик мовчазної втрати змін.
- Низький поточний біль + відсутність дедлайну — ризик, що проєкт зупиниться на півдорозі.

## 13. Recommendation
**Selected: Approach A — One-Page Content Fix Console (чистий, без запобіжників).** RICE = 5 (§11) — низький, без дедлайну й без доведеного PMF, тож правильна ставка — найдешевший варіант, а не золочення. Feasibility підтверджено по всіх трьох блоках (§12: Tech/Skills/Time ☑), тож A будується без нового фундаменту. Синтез-матриця дає A подвійний плюс Engineer·Exec (§8: «мала поверхня, швидко» + «найдешевше зняти біль»), тоді як B programує `-` в Engineer і UX на цій стадії. Конкурентна прогалина (§6) закриває питання «чому не взяти готове»: Retool/Directus/Strapi — generic CRUD, не знають доменної семантики «скарга → правка» й «правильна відповідь», тож тонка доменна консоль дає більше за менше, ніж налаштування generic-інструмента. Користувач свідомо обрав варіант без історії/відкату — цей trade-off зафіксовано як прийнятий ризик (§10), а не як прогалину.

**Locked-in pointer**: write-prd описує саме Approach A — одну консоль із чотирма сутностями (слова/леми, скарги, учні, списки/CEFR-набори), editor-first, admin із базовим переглядом учнів, без версіонування/відкату та без UI-керування ролями. Мітигацію silent answer-key drift PRD виносить як відкрите питання, не як AC v1.
