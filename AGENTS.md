# Правила для агентів у проєкті

## Авторство комітів

- Не додавай АІ-моделі, асистентів, агентів або їхніх постачальників як авторів чи співавторів комітів.
- Не додавай для них трейлери `Co-Authored-By`, підписи чи інші позначки авторства в повідомлення комітів, зокрема автоматично додані інструментами.
- Зберігай налаштоване користувачем авторство Git і справжнє співавторство людей. Перед створенням коміту перевіряй його повідомлення на відсутність позначок авторства АІ.

## Формат повідомлень комітів

- Використовуй Conventional Commits: `<type>[(<scope>)][!]: <опис>`.
- Пиши тип і необов’язкову область змін (`scope`) англійською малими літерами, а опис і тіло повідомлення — українською. Зберігай технічні назви без перекладу.
- Обирай тип за змістом зміни:
  - `feat` — нова функціональність.
  - `fix` — виправлення помилки.
  - `docs` — зміни лише документації.
  - `refactor` — перебудова коду без зміни його поведінки.
  - `perf` — покращення продуктивності.
  - `test` — додавання або зміна тестів.
  - `style` — форматування коду без зміни поведінки, наприклад відступи чи пробіли.
  - `build` — зміни системи збирання або залежностей.
  - `ci` — зміни конфігурації та сценаріїв CI/CD.
  - `chore` — інші службові зміни, що не підпадають під наведені типи.
  - `revert` — скасування попереднього коміту; у тілі вкажи його хеш і причину.
- Додавай `scope`, коли він уточнює підсистему, наприклад `api`, `auth`, `docs`. Для тієї самої підсистеми використовуй однакову назву.
- Після двокрапки став один пробіл. Починай опис із дієслова в наказовій формі з малої літери: «додай», «виправ», «онови». Не став крапку наприкінці заголовка.
- Обмежуй заголовок 72 символами. Описуй конкретну зміну; уникай загальних повідомлень на кшталт `fix: виправ помилки`.
- За потреби додавай тіло після порожнього рядка: поясни причину зміни та суттєві наслідки.
- Для несумісних змін додавай `!` перед двокрапкою та пояснення в тілі з маркером `BREAKING CHANGE:`.
- Один коміт має містити одну логічну зміну. Розділяй незалежні зміни на окремі коміти, щоб кожен мав точний тип і опис.
- Дотримуйся цього формату також для підсумкових повідомлень squash-комітів.

Приклади:

```text
feat(auth): додай вхід через одноразовий код
fix(api): виправ перевірку порожнього запиту
docs: опиши правила повідомлень комітів
chore: онови налаштування редактора
feat(api)!: зміни формат відповіді на запит

BREAKING CHANGE: поле result замінено на data; онови клієнтів API.
```

## Мова документації та коментарів

- Веди авторську документацію проєкту українською мовою.
- Пиши українською всі авторські коментарі в коді, зокрема XML-коментарі, коментарі в тестах і конфігураціях.
- Українською оформлюй пояснення, заголовки, примітки, підписи й повідомлення для розробників.
- Назви файлів і папок документації пиши англійською (наприклад, `architecture-map.md`, `docs/features/`). Українською має бути вміст документів, а не їхні назви.
- Не перекладай назви типів, методів, змінних, API, команд, шляхів, ключів конфігурації, форматів даних, власних назв і дослівних цитат, якщо це порушить точність або синтаксис.
- Зберігай потрібні інструментам маркери й коментарі, зокрема `auto-generated`, pragma, nullable та успадковану документацію. Не редагуй згенеровані файли вручну, якщо це не є окремою вимогою.
- Залишай приклади коду й команди виконуваними; перекладай лише коментарі та пояснювальний текст.

## Структура й наочність

- Для процесів, архітектури, потоків даних і переходів станів використовуй Mermaid-діаграму, якщо вона пояснює зв’язки простіше за довгий опис.
- Пиши короткі валідні діаграми, що показують актуальну реалізацію або явно позначену пропозицію.
- Не додавай діаграму, коли достатньо одного речення чи короткого списку.
- У документації відокремлюй поточну поведінку від запланованих можливостей і невирішених питань.

## Зв’язність документів

Документація — це граф, а не набір ізольованих файлів: з будь-якої згадки має бути один клік до джерела (у дусі Obsidian, але зі стандартним markdown, що працює на GitHub, у VS Code та Obsidian).

- Кожна згадка іншого документа, ADR, задачі чи розділу — клікабельне **відносне markdown-посилання**: `[ADR-0007](adr/0007-dispatch-notifications-through-postgres-dispatch-table.md)`, `[T20](tasks/T20-dictionary-import.md)`. Лінкуй кожну згадку, не лише першу в розділі.
- Посилання на розділ веде на якір заголовка: `[PRD §6](PRD.md#6-non-functional-requirements)`. Якщо заголовок підрозділу не має стабільного якоря, веди на файл.
- Не використовуй `[[вікілінки]]` і голі згадки на кшталт «див. ADR-0007» без посилання. Шляхи завжди відносні до поточного файлу, без абсолютних.
- Не лінкуй усередині fenced-блоків, inline-коду й заголовків: заголовки змінюють якорі.
- Нові документи заводь із зворотними зв’язками: ADR посилається на PRD, SAD і пов’язані ADR; задача — на AC, ADR і залежності.
- Після перейменування чи переміщення файлу або зміни заголовка запусти перевірку та виправ усе, що вона знайде:

```bash
python tools/docs/check_links.py
```

Скрипт перевіряє існування файлів і якорів у всіх md-файлах і падає на бітих посиланнях та залишках `[[вікілінків]]`. Виконуй його перед комітом будь-яких змін у `*.md`.
